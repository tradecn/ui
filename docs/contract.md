# The item contract

Every item in `registry.json` passes these rules before it merges. `scripts/validate-registry.ts` checks them mechanically; ESLint enforces the import and JSX rules while you type. The point of the contract is the guarantee on the README: a shadcn release can restyle, rebase, or rewrite its components underneath a tradecn consumer and the tradecn files keep working, because they only ever touch shadcn through the consumer's own `@/components/ui/*` exports.

1. Types. `registry:ui` for `registry/tradecn/ui/*`, `registry:hook` for `hooks/*`, `registry:lib` for `lib/*`, `registry:block` for `blocks/*` with explicit `target`s, `registry:theme` for the opt-in theme items only. `registry:component` is not used.
2. No tradecn item in `registryDependencies`. The GitHub form of `shadcn add` does not carry a `#ref` into dependencies, so an item pinned to `v0.1.0` would pull its siblings from `main`. Shared code rides along in each item's `files[]` with a per-file `type`; duplicates across items are byte-identical and deep-merge cleanly.
3. `registryDependencies` are bare shadcn built-in names, each present in `registry/tradecn/builtins.lock.json` with the exported symbols tradecn uses, locked for `radix-nova`, `base-mira`, and `base-vega`. `just lock-builtins-check` refetches upstream nightly.
4. Imports inside registry source take one of four forms: own files as `@/registry/tradecn/{ui,hooks,lib}/x`, shadcn built-ins as `@/components/ui/x`, `import { cn } from "cn"`, or an npm package that is in `dependencies` and in `registry/tradecn/deps.allow.json`. Never relative paths, never `@/lib/utils`, never `radix-ui`, `@radix-ui/*`, `@base-ui/*`, `cmdk`, or `react-resizable-panels`.
5. No `asChild`, `render`, or `nativeButton` on shadcn triggers. Style the trigger's own element with `className` or pass children. When a trigger must wrap a tradecn element, give it `className="contents"`.
6. `dependencies` are `name@^x.y.z`, the range from the allowlist, and every declared dependency is imported.
7. `cssVars` are generated by `just tokens` from `registry/tradecn/tokens.json`, for the tokens the item's files use. Values are literal `oklch(...)` or `var(--color-<shadcn token>)`; those are the two forms the CLI turns into Tailwind utilities. `registry:ui` items never overwrite a consumer's existing variables, so a consumer's own `--up`/`--down` survive every later `shadcn add`.
8. `css` blocks hold only `@keyframes tradecn-*` and `@layer components` restyles of third-party classes. A restyle's selector starts from a class of the third-party package (`.dockview-theme-tradecn`, `.dv-*`), never from an element, a shadcn class, or a tradecn slot: those are styled in the source files. A third-party stylesheet is unlayered and beats `@layer components` on the same element, so a restyle sets the package's own custom properties rather than fighting its rules.
9. `title`, `description`, and `categories` are required; `docs` is required when an item has `css`, `cssVars`, or a dependency beyond `cn`; `meta.components` names real exports.
10. The item's name is its primary file's basename, and a `registry:ui` root element carries `data-slot="tradecn-<name>"`.

11. A built-in that needs a provider in any base gets one from the item. Radix tooltips throw without a `TooltipProvider` above them and Base UI tooltips do not care, so an item that uses `tooltip` wraps itself in the `TooltipProvider` every style exports, with no props (the prop names differ by base). The export lock cannot see this kind of difference; the browser matrix does, which is why every item has a smoke scene in all three consumers.

12. No two files in one item share a basename, whatever their directories or extensions. When the CLI (4.21.0) rewrites an item's own imports it collects every file in the item whose name matches, sorts `.tsx` ahead of `.ts`, and only breaks a tie by the path that was asked for. So `lib/sparkline.ts` beside `ui/sparkline.tsx` installs a component whose import of its library points back at itself, and the consumer's typecheck fails with a circular import. Nothing before the install can see it: the source resolves correctly, and so does the built JSON. The validator checks it; `sparkline-geometry.ts` is named that way because of it.
13. A `registry:theme` item is its `cssVars` and nothing else: no files, both `light` and `dark` present, and every tradecn token set in each, so a token added later cannot be left at a value tuned for the background the theme replaced. Colors take the same two forms as everywhere else. `just tokens` leaves a theme alone. It has to: a theme has no files, so "the tokens its files use" comes to nothing, and writing that back deletes the theme. The validator rejects an empty one. A theme is the only kind of item that overwrites a consumer's variables, and its docs say so first.

How a consumer updates: `npx shadcn add tradecn/ui/<item>#v0.2.0 --diff` to review a tradecn change, `npx shadcn add table --diff` to review a shadcn change underneath. Neither touches the other's files.

## What a version means

The tag is the version, and from `v0.1.3` on it is semver with no pre-1.0 exceptions.

- A **major** (`v1.0.0`, `v2.0.0`) means a file you installed changed its API: a prop, an export, a hotkey, a token name, a `data-slot`. The release notes say what moved under ⚠ Breaking Changes. `--diff` before you take it.
- A **minor** means new items or new props. What you installed keeps working as it did.
- A **patch** means a file changed and its API did not: a fix, a performance change, a refactor, a tidy. `--diff` shows you the bytes.

Docs, CI, and test changes cut no release, so tradecn.dev shows the docs of the tag it serves. [`CONTRIBUTING.md`](https://github.com/tradecn/ui/blob/main/CONTRIBUTING.md) says how a pull request title picks the bump.
